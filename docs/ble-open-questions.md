## 已确认并按此实现

1. **UUID 暂不调整。** 当前联调继续使用 Service `0x181F`、RX `0x2B30`、TX `0x2B31`。它们与 Bluetooth SIG 已分配用途存在冲突，但现阶段不阻塞开发板联调；固件正式定版前再评估私有 128-bit UUID。
2. **广播包为 25 字节。** `pending` 是后加入字段，因此 Service Data 自定义 value 按 4 字节解析：电量、状态、模式、`pending`。原文档中的 24 字节和“自定义数据 3 字节”属于未更新内容。
3. **UUID 显示顺序由 App 兼容。** 这一项的意义不是要求硬件增加字段，而是避免 Android/iOS 将同一组 128-bit UUID 字节显示成相反顺序，导致 App 扫描到设备却识别失败。App 已同时兼容文档顺序和整段字节反序；真机联调时保留一次原始扫描日志即可。
4. **MTU 由底层协商。** Android App 连接后主动请求 MTU 247，预期可提供约 244 字节 ATT 载荷，能够容纳最大 195 字节数据帧；iOS 由系统协商，App API 不主动设置。实际协商值和完整帧 Read 仍需开发板真机日志验证。
5. **当前固件没有同帧重传。** App 遇到 CRC、SOF/EOF、长度或 Offset 错误后立即中止本轮传输，不会继续向后 Read 造成跳帧；用户重新连接后从头拉取。文档中“CRC 失败后重读同一偏移，最多 3 次”暂不作为当前能力。
6. **BlockID 只在一次上传期间有效。** 每轮从 1 开始，与端侧开关机无关。App 不跨传输保存或续接 BlockID。
7. **Block 内部业务格式暂未确定。** App 只按音频、运动、混合三种 Type 保存原始 Payload，不把未知数据伪装成 WAV。
8. **App 必须先持久化再等待上传。** 每个完整 Block 在拉取过程中立即写入 App document 目录的待上传队列，并记录设备码、BlockID、Type、长度和 SHA-256。原始文件不会因 App 重启或系统清理 cache 而丢失；只有 Backend 明确确认上传成功后，才允许调用删除接口。
9. **策略目标是尽快上传。** 前台发现 `pending=1` 后应尽快连接、保存并触发上传；网络不可用时保留本地队列，网络恢复后重试。Android/iOS 后台扫描和后台上传的具体能力需要后续真机验证。
10. **设备遥控协议尚未实施。** 当前两份文档只支持广播和数据传输；声音、振动、电击、止吠灵敏度以及执行结果通知不属于已完成协议。

## 剩余需要确认

1. **正式绑定标识。** 当前开发联调临时使用 `XG/ZF + 8位广播SN`。正式二维码中的设备编号、广播 SN、设备类型和 Backend 设备记录如何对应，待产品编码方案确定。
2. **实机 MTU 结果。** Android 请求 247 后开发板实际返回多少；iOS 实际协商多少；两个平台是否都能一次 Characteristic Read 返回完整 195 字节帧。
3. **结束空响应。** 最后一帧后，固件实际表现是成功返回 0 字节 value、ATT error、重复最后一帧，还是主动断开连接。
4. **BlockID 上限表述。** 帧字段为 2 字节无符号整数，可表示的最大非零 ID 是 `65535`；“不会超过 65536”需要确认是指最多 65535，还是指共有 65536 个取值。
5. **Block Payload 格式和稳定记录 ID。** 需要补充音频编码/采样参数、IMU 字段与单位、混合数据分段、采集时间，以及跨重连可识别同一记录的稳定 ID。没有稳定记录 ID 时，传输中断后从头读取可能在本地产生重复 Block。
6. **端侧删除的精确时机。** 需要确认端侧是在返回最后一帧、返回空响应还是断开连接时删除数据；如果 App 文件写入失败或连接中断，端侧是否仍保留整轮数据。空间有限可以理解，但删除必须晚于 App 已拿到完整数据的时点。
7. **CRC 重传是否永远不做。** 如果后续仍不实现同帧重传，应同步删除协议文档中的“CRC 失败重新 Read 同一偏移”描述；如果要实现，需要定义 ACK/NAK 或 Offset 控制命令。
8. **前后台边界。** Android 是否使用 foreground service；iOS 在后台能否扫描、连接并完成拉取；系统杀进程、蓝牙关闭和网络切换后的恢复策略需要真机验证。
9. **设备遥控协议。** 后续需要单独提供服务/特征 UUID、命令字节、参数范围、写入方式、执行成功通知和错误码。
